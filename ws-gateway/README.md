# ws-gateway

WebSocket/STOMP-шлюз — единственный способ для клиента узнать о прогрессе задачи без polling'а. Обращается только к Kafka и Redis за актуальным состоянием. Масштабируется горизонтально (`--scale ws-gateway=N`).

## Подключение

STOMP-эндпоинт: `ws://.../ws` (через nginx — `/ws`, с апгрейдом соединения).

| Destination | Когда приходит | Payload |
|---|---|---|
| `/topic/job/{job_id}` | задача завершена (`DONE`/`ERROR`) | `JobStateResponse` |
| `/topic/job/{job_id}/queue` | обновилась позиция в очереди | `JobQueueResponse` |

Destination `/topic/*` для клиента `read-only` — заблокировано через `ExternalMessageInterceptor`. Для шлюза `write-only`.

## Откуда берутся данные

Сервис слушает оба Kafka-топика отдельной consumer-группой (`group-id=ws-gateway`), независимой от группы `processor`. Все инстансы шлюза входят в одну группу, и партиции топиков распределяются между ними: каждое сообщение читает тот инстанс, которому досталась его партиция. Поэтому состояние, нужное всем инстансам, вынесено в Redis:

- **Очередь задач** — Redis ZSET `queuePositions`. Сообщение из `topic:queue` добавляет задачу (score — время из UUIDv7, т.е. порядок постановки), сообщение из `topic:result` удаляет. Позиция задачи — её ранг в ZSET + 1, одинаковый для всех инстансов.
- **Финальный статус** (`DONE`/`ERROR`) — инстанс, прочитавший событие из `topic:result`, публикует его в Redis-канал `receivedJobResults`. Сообщение получают все инстансы, и каждый пушит статус своим подключённым клиентам.

## Подписки и позиция в очереди

Каждый инстанс хранит в памяти реестр своих подписок на `/topic/job/{job_id}/queue` (`SubscriptionRegistryService`). Это позволяет определить, кто из его клиентов следит за какой задачей и какая позиция была отправлена последней.

- **При подписке** клиент сразу получает текущую позицию из ZSET.
- **При получении события завершения задачи** инстанс одним pipeline-запросом пересчитывает ранги всех своих подписанных задач и рассылает только те позиции, которые уменьшились.
- **`UNSUBSCRIBE` и `DISCONNECT`** сообщения удаляют подписки из реестра (`UnsubscriptionMessageInterceptor`).

## Подписка после завершения

Если клиент подписался на `/topic/job/{job_id}` уже после того, как задача завершилась, событие из Kafka он пропустил. Для этого `SubscriptionMessageInterceptor` при подписке читает статус задачи из Redis и сразу отправляет его, если он терминальный (`DONE`/`ERROR`).

## Гонка `queue` / `result`

Топики `queue` и `result` читаются независимыми контейнерами, а значит порядок между ними не гарантирован. Если `result` придет раньше, чем задача из `queue`, то удаление из ZSET очереди случится раньше добавления, в конечном счете завышая очередь до очистки через `RedisCleanerScheduler`.

Решением послужила защита через доп-отметку:
- при получении сообщения из `result` сначала ставится отметка `finished:{job_id}` с TTL в 1 час, и только потом задача удаляется из ZSET. Если сделать наоборот, задача из `queue` может успеть добавиться в промежутке между удалением и отметкой и снова застрять в очереди;
- при получении сообщения из `queue` атомарно проверяется наличие отметки, и задача добавляется в ZSET, только если отметки нет.

## Очистка очереди

`RedisCleanerScheduler` раз в час удаляет из ZSET задачи старше суток (по score) — страховка от задач, результат которых так и не пришёл.

## Обработка ошибок

Общая схема (DLT, повторы, классификация ошибок) — в [корневом README](../README.md#обработка-ошибок-kafka). Специфика сервиса:

- **`topic:result`** проверяется `ResultMessageValidator`. Невалидные события уходят в `result-dlt`.
- **Ошибки Redis**, полученные в ходе обработки сообщений из Kafka, приводят к бесконечному повтору с нарастающей паузой. Таким образом событие не теряется, а идет ожидание восстановления Redis. Pub/Sub-подписка после падения Redis восстанавливается сама.

## Переменные окружения

Как и `api`, сервис не запускается в одиночку — все значения приходят из compose-файлов в корне проекта: Kafka (`KAFKA_BOOTSTRAP_SERVERS`), Redis (`REDIS_HOST`/`REDIS_PORT`). Порт сервиса — `8081` (см. `application.properties`).

Как поднять сервис целиком — см. [корневой README](../README.md).
